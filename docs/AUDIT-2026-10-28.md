### Lens: moodle-standards

#### `amd/src/entry_points.js:25`: jQuery imported in new AMD code (info)
- Evidence: `import $ from 'jquery'` is used once, at about line 104 (`$(document).on('cie:accessibleChange', ...)`). An in-code comment justifies it: `core/custom_interaction_events` fires a jQuery event that native listeners cannot see.
- Build check: `amd/build/entry_points.min.js` contains `cie:accessibleChange` (grep count 1), and the build shares history with its source (42b43e2). No full rebuild was compared.
- Recommendation: keep it. Name the core module and version in the comment, so the import is dropped once core fires a native event.

#### `amd/src/quick_compose.js:58` (lines 56-61): toast built from interpolated HTML (minor; security-client: info)
- Evidence: the code is ``addToast(`${sent} <a href="${url.href}">${view}</a>`)``. `sent` and `view` are lang strings: 'Message sent' and 'View message' (lang/en lines 173 and 288).
  - security-client reports that `core/toast` renders the message as HTML. moodle-standards did not re-read the core template.
  - The URL is built with `URL`/`searchParams`. `messageid` is a server int (quick_compose.php:228) wrapped in `String()`.
  - No user-controlled value reaches the markup. The remaining risk is a translation containing `<` or `&`.
- Recommendation: build the toast body through a Mustache partial with `{{#str}}` and an escaped link, or escape `sent` and `view` before interpolating.

#### `classes/form/quick_compose.php:78`: maxlength and required rules are client-side only (info)
- Evidence: the rules are `addRule('subject', ..., 'required', null, 'client')` and `'maxlength', 100, 'client'`. `validation()` (lines 123-125) rechecks only the empty subject.
  - A longer subject is cut by `message::update()`, as the comment at line 77-79 says. The comments lens confirmed the cut against message.php:903-905 (97 characters plus '...').
  - `tests/form/quick_compose_test.php` covers the empty subject (`test_rejects_empty_subject`) and has no over-length case.
- Recommendation: pin the truncation in a test, or add the maxlength check to `validation()`. Low priority.

#### `classes/local/entry_points.php:112` (lines 110-117): sesskey in GET links that create a draft (info; also security-client at :116)
- Evidence: `compose_url()` adds `'sesskey' => sesskey()` to `/local/mail/create.php`. The quick-compose form does the same (quick_compose.php:78-83).
  - `create.php` calls `require_sesskey()` and then `message::create()`, so a GET writes a draft. The lenses cite different lines: moodle-standards gives :30-31 and :66, security-client gives :35.
  - The key belongs to the viewer and goes only to a same-origin URL. It can still reach browser history, a copied link or a Referer.
  - The unvalidated-recipient part of this finding is merged into the major finding under privacy-capabilities-ws.
- Recommendation: this is an accepted Moodle pattern. If tightened, make `create.php` a POST (`single_button`).

#### `classes/privacy/provider.php:209`: dynamic lang string id (minor)
- Evidence: `'color' => get_string('color' . $label->color, 'local_mail')`. This breaks the fleet rule "no dynamic ids". A literal scan found no missing key, but it cannot see this id.
- Recommendation: use `match ($label->color) { 'red' => get_string('colorred', ...), ... }` or a static map of literal calls.

#### `lib.php:128` (lines 128-143): html_writer in shipped PHP (minor)
- Evidence: the navbar envelope is built with `html_writer::tag/span/div` and an inline `style => 'font-size: 16px'`.
  - The same helper appears at view.php:103-104 and classes/output/renderer.php:261 and :274.
  - The fleet rule is zero html_writer. The plugin has only two Mustache templates (notification_html and notification_text).
  - This is upstream code and html_writer is not deprecated, so no gate fires. It breaches the fleet standard only.
- Recommendation: move the navbar markup to a Mustache template with an `Example context (json):` block, and put the font size in `styles.css`. `view.php` and `renderer.php` can stay as upstream divergence.

#### `tests/local/mtube_provider_test.php:42`: MooTube provider tests and Behat never run in CI (minor)

#### `view.php:104`: initial-data JSON inlined in a script tag without HEX flags (info; also security-server)
- Evidence: `html_writer::script('window.local_mail_view_data = ' . json_encode($data))`. `$data` holds settings, the viewer's preferences and all lang strings (lines 91-96).

#### `classes/external.php:2155` and `create.php`: draft recipients go unvalidated, so any user's name, picture and profile can be read back (major; merged from four lenses)
- Lenses:
  - privacy-capabilities-ws: major.
  - security-server: major.
  - security-client: minor ("upstream behaviour; low-sensitivity fields").
  - moodle-standards: info, raised as an open question at entry_points.php:112.
- Write paths:
  - `update_message` sends the posted to/cc/bcc ids straight to `user::get_many()`. Lenses cite external.php:2153-2157, :2155 and :2149-2153.
  - `create.php` does the same with `?recipients=` (PARAM_SEQUENCE, protected only by sesskey). Lenses cite :60-61, :62-65 and :69.
  - `user::get_many()` drops only deleted users and the guest (classes/user.php:143; picture fields at :145).
  - `message::update()` stores every id as a `local_mail_message_users` row (message.php:972-1000).
- Missing check: reachability (enrolment, usemail, mailsamerole, separate groups) is checked only in `sender::check_recipients()` (sender.php:57), at send time (sender.php:93).
- Read paths:
  - `get_message_response` (external.php:985-1006) returns firstname, lastname, fullname (:1000), pictureurl and profileurl for every non-BCC recipient.
  - `$validrecipients` is computed at :990-993 but used only for the `isvalid` flag.
  - `search_messages_response` is similar (around :773-782, :778).
- Feeders:
  - The quick-compose "open full editor" link (quick_compose.php:81-87) and the no-JS profile link (entry_points.php:110-117) both lead into this unchecked path.
  - Quick compose itself names only reachable users (quick_compose.php:239-255).
- Impact (inferred): a user with usemail in any course can read the identity of any non-deleted site user by id. That includes users in other courses, users outside the reader's group under separate groups, and teachers.
- Tests: the only recipient test found (tests/external_test.php:2389) covers the send path. It was not run.
- Line ranges differ between lenses, so re-read before fixing.
- Recommendation:
  1. In `get_message_response` and `search_messages_response`, return name, picture and profile only for ids in `$validrecipients`. Return the id with a generic deleted-user-style label for the rest.
  2. Also drop unreachable ids in `update_message` and `create.php`, using the `user_search` or `check_recipients` logic without the throw.
  3. Add a test: a draft addressed to an unenrolled user must not expose that user's name through `get_message`.

### Lens: security-server

#### `classes/course.php:97` (lines 97-99): hidden courses are not excluded from mail (info)
- Evidence: `enrol_get_users_courses($userid, true)` is filtered by `has_capability(usemail)` only. There is no `visible` or `moodle/course:viewhiddencourses` check, and the external functions call only `validate_context(system)` (external.php:2223).

#### `classes/external.php:2033` and `:2073`: reply_message and forward_message accept the sender's own unsent draft (minor)
- Evidence: both gate on `user::can_view_message()`, which is true for the sender's own draft. `message_data::reply` and `message_data::forward` guard `!$message->draft` only with `assert()` (message_data.php:230, 157), which is compiled out in production.
  - Once the reply is sent, a recipient who did not take part gets the draft's subject, body and attachment URLs through references (external.php:1024 skips only participants).
  - Forward copies the draft's attachments. The content is the sender's own.
- Recommendation: throw `errormessagenotfound` when `$message->draft` instead of relying on `assert()`.

#### `classes/local/sender.php:57`: the reusable recipient API does not check that the sender can use mail (minor)
- Evidence: `sender::check_recipients`, `entry_points::can_mail` (entry_points.php:91) and `user_search` never test the sender's enrolment or usemail.
  - Every current caller checks first.
  - `quick_compose::definition()` runs `recipient_summary()` (around quick_compose.php:176-190) before `check_access_for_dynamic_submission()`. No leak was shown.
  - Core's dynamic_form ordering was not verified.
- Recommendation: make `check_recipients` and `can_mail` fail unless `$sender->can_use_mail($course)`.

#### `classes/local/sender.php:98`: the message is marked sent before recipients are notified (info)
- Evidence: `$message->send(time())` runs and the event fires before the `message_send` loop (:104-109).
  - The mailbox path (external.php:2191-2204) has no transaction, so a processor failure mid-loop leaves part of the notifications undelivered.
  - There is no lock against two concurrent sends. The quick-compose path does use a transaction.
- Recommendation: catch and log notification failures per recipient. Optionally take a core lock on the message id.

#### `classes/message.php:894`: update() saves files to the request's course context when the draft has references (minor)
- Evidence: `$newcontext` comes from `$data->course`, but the course is reassigned only when there are no references (around :899-901).
  - For a reply or forward draft, files go to another course's context while `courseid` stays the same, and the old area is deleted (around :1020-1022).
  - Listing and serving then find nothing (external.php:~954, download.php:51).
  - Only the draft owner can cause this. No cross-user exposure was found.
- Recommendation: compute the context from `$this->course` after the course decision, and reject a different courseid when references exist.

#### `classes/user_search.php:151` (lines 151-160): same-role exclusion and the separate-groups rule read only course-context role assignments (info)
- Evidence: the mailsamerole subquery joins `role_assignments` on the course context only. Roles assigned at category or system level are invisible to it, for the sender and for the candidate.
  - The separate-groups block (around :163-181) reads the right facts.
  - This is upstream behaviour and was not run.
- Recommendation: if category-level assignments are in use, walk the parent contexts, or document the limit in the README.

#### `svelte/src/components/CourseSelect.svelte:108`: course name is decoded to plain text, then injected with `{@html}`, a stored XSS (major)
- Chain:
  1. `courseHtml()` (CourseSelect.svelte:35-38) calls `formatCourseName()`.
  2. `formatCourseName()` (utils.ts:64-74) returns `convertHtmlToText(fullname|shortname)`.
  3. `convertHtmlToText()` (utils.ts:33-36) sets `innerHTML` and returns `innerText`, which is decoded text.
  4. Line 108 renders that text through `{@html}` with no re-escape. Only `<mark>` is added.
- Server side: `util::format_string()` (external.php:392-393, 805-806, 951-952) follows Moodle 5.2's `lib/classes/formatting.php:108-125`. On the default path (striptags off), the entity `&lt;img src=x onerror=alert(1)&gt;` survives and is decoded into a live `<img onerror>`.
- Actor and victims: the actor is anyone allowed to edit a course name (moodle/course:update, a course creator, a manager). The victims are every mail user of that course, admins included.
- Not reproduced. Two preconditions are unconfirmed:
  - PARAM_TEXT keeps a typed `&lt;` in the course edit form.
  - The outcome is unchanged with `formatstringstriptags=1`.
- Recommendation:
  - Escape the decoded name and the matched segments in `courseHtml()`, or drop `{@html}` and render `<mark>` with Svelte nodes in `{#each}`.
  - Add a vitest case with the course name `&lt;img src=x onerror=1&gt;` asserting that no `<img>` appears.
  - Reproduce it on a stack before release.

#### `svelte/src/components/View.svelte:68`: postMessage and the message listener ignore origin and source (minor)
- Evidence: lines 67-69 and 106 post the mailbox title, loading state and clicked link hrefs to `window.parent` with `'*'`.
  - `handleMessage` (:90-94) trusts any message whose `data.addon == 'local_mail'` and never checks `event.source` or `event.origin`.
  - A message with null data throws a TypeError.
  - Impact: a mobile-layout navigation reset, and titles and URLs leaked to whatever page frames it. Moodle's X-Frame-Options default limits who can frame the page.
  - This is inherited upstream code.
- Recommendation: check `event.source === window.parent`, and use `event.data?.addon`. Pin the outgoing origin if the Moodle App's origin allows it, or document why `'*'` is needed.

#### `svelte/src/lib/utils.ts:35` (lines 33-36): `convertHtmlToText` parses server strings with `innerHTML` on the live document (minor)
- Evidence: a detached DIV still starts `<img onerror>` loads. Today the input is `format_string` output, which `clean_text` purifies (formatting.php:125), so this alone is not exploitable.
- Used at: Menu.svelte:154, CourseBadge.svelte:17, CourseLink.svelte:27-30 and View.svelte:57. This is defence in depth, and it is the source half of the major XSS above.
- Recommendation: use `new DOMParser().parseFromString(html, 'text/html').body.textContent`, and keep the result out of every `{@html}` sink.

## 6. Verification of the major findings (after the workflow)

The workflow verifies blocking findings only, and this audit had none, so each major code finding
was handed to its own `fleet-verifier` afterwards, with the instruction to refute it.

| Finding | Verdict | Severity after verification |
|---|---|---|
| `svelte/src/components/CourseSelect.svelte:108`: course name rendered with `{@html}` | **Confirmed** | **blocking** |
| `classes/external.php:2155` and `create.php:63-66`: draft recipients unvalidated, names read back | **Confirmed** | major |

- **CourseSelect XSS.** A literal `<img ...>` in a course name is stripped by `format_string`, but an
  entity-encoded one (`&lt;img src=x onerror=...&gt;`) survives `PARAM_TEXT` and
  `core_external\util::format_string` unchanged (run in the m503 container).
  `svelte/src/lib/utils.ts:33-37` (`convertHtmlToText`) decodes it back to markup, and
  `CourseSelect.svelte:35-38,108` injects it with `{@html}` for every course in the dropdown, on page
  load. A user who can rename a course (editing teacher, manager by default) can run script in
  the mailbox of everyone enrolled there, administrators included. Not exploitable with
  `formatstringstriptags = 0`. Fix: escape each plain-text segment in `courseHtml()` before
  wrapping matches in `<mark>`, rebuild `svelte/build`, and pin it with an `&lt;img ...&gt;` name.
- **Draft recipient oracle.** `create.php` and `external::update_message` store any non-deleted,
  non-guest user id as a draft recipient (`classes/user.php:135-150`, `classes/message.php:970-1017`),
  and `external::get_message_response()` (~990-1004) returns their names, picture and profile URLs,
  only flagging `isvalid`. `tests/external_test.php:754-778` pins that behaviour. Reachability (rule
  G1 included) is checked only at send. Fix: filter ids not already on the draft through
  `user_search` at write time (drop silently in `create.php`, throw `errorinvalidrecipients` in
  `update_message`), and redact invalid recipients of drafts in `get_message_response()` to cover
  drafts that already hold such rows.

Related, same class as the XSS: `amd/src/quick_compose.js:58` builds the toast from two lang strings
interpolated into HTML (section 4, minor).
